# Connect end to end, with vanguard for REST

The browser speaks the Connect protocol to generated clients, so that the shape a page reads is
the shape the proto declares. The backend serves Connect, gRPC, gRPC-Web and REST from one
handler using `connectrpc.com/vanguard`, which transcodes REST at runtime from the
`google.api.http` annotations the OSAC standards already require. This replaces the
hand-written JSON the BFF produced and the hand-written TypeScript the frontend consumed.

## Why not keep grpc-gateway

The backend serves REST today through grpc-gateway's **in-process** registration
(`internal/restgateway/server.go`, `RegisterClustersHandlerServer`), whose handlers take
grpc-go service implementations. connect-go generates a different handler interface, so
adopting Connect breaks that path outright — the choice could not be deferred. The options were
vanguard (one handler, four protocols, no `.pb.gw.go` codegen), grpc-gateway dialling the
Connect server over loopback (mature, extra hop, keeps the gateway codegen), two parallel
implementations (rejected outright: it reintroduces the duplication this work exists to remove),
or dropping REST (rejected: the backend's `AGENTS.md` requires flat REST under `/api/`, and OSAC
describes its fulfillment service as gRPC/REST).

`mpaulgreen/osac-service-standards` names grpc-gateway as the REST gateway and does not mention
Connect or vanguard. We read the standard as constraining the **observable contract** — the
`google.api.http` annotations, the flat URL space, the status-code mapping — and not the
transcoder, and vanguard honours all of that. The committed OpenAPI document is generated by
`protoc-gen-openapiv2` from the same annotations and is unaffected by which transcoder serves
them, which removes the strongest argument for keeping the gateway.

Vanguard is Alpha and mid-rewrite onto connect-go v2. We accept that because the decision is
cheap to reverse: both read the same annotations, so falling back to grpc-gateway over loopback
is a change to `main.go`, not a re-architecture. **grpc-gateway over loopback is the named
fallback.**

## The frontend

`@connectrpc/connect-query` over TanStack Query v5, with types from `protoc-gen-es` v2 (plain
objects for proto3). The console generates TypeScript locally from `.proto` files fetched from
the backend; publishing a Buf Schema Registry module is the better end state but needs a
pipeline nobody owns yet.

Deleted: `useServiceData`, `HttpConsoleService`, `ConsoleService`, `MockConsoleService`,
`frontend/src/api/types.ts` and `frontend/src/api/adapters.ts`. Zod stays for form input only —
validating a response whose type is already generated is a fourth declaration of the same shape.

## Consequences

- The `{"data": ...}` / `{"meta": ...}` envelope, the `ETag`/`If-Match`/428 protocol, and the
  HTTP status table all disappear. Optimistic concurrency moves to the version field in the
  request message with `lock: true`, which the proto already carries. Most of
  `docs/plan/bff-api.md` and all of `mock/examples/` go with them.
- Pages read proto shapes. A thin typed selector layer is allowed for presentation, but any
  derivation that encodes a policy or a meaning — "is this cluster a grid member", "what phase
  is this model in" — must become a proto field. Otherwise the BFF's "Known exceptions" simply
  relocate into React, where they would be unversioned, untested and invisible to the backend.
- Paging uses `useInfiniteQuery` against `offset`/`limit`; the UI's polling becomes
  `refetchInterval`.
